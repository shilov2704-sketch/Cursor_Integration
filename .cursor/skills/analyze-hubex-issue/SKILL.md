# Анализ проблемы HubEx

Команда: `@Cursor сделай анализ` (и синонимы: проанализируй, разбери причину, анализ кода).

**Не создавай Bug.** Не вызывай `wit_create_work_item` и не запускай `create-hubex-bug.mjs`.

Этот репозиторий (`Cursor_Integration`) — не код продукта. Код HubEx читай через MCP `ado` / `user-ado`. Карта репозиториев: `ado/code-repos.json`.

## Шаги

1. Прочитай тред: тенант, страница/форма, действия, фактический результат, скриншоты.
2. Определи платформу (web / mobile / backend) по тем же правилам, что для багов. Неясно → web, плюс связанный backend-сервис.
3. Выбери репозитории из `ado/code-repos.json`. При необходимости `repo_list_repos_by_project` с `project=HubEx`.
4. Ищи код MCP-инструментами:
   - `search_code` — `project: HubEx` (или массив), `searchText` по экрану/API/компоненту, `top` 10–20. Можно сузить `repository`.
   - `repo_get_file_content` — прочитай найденные файлы. Если `repositoryId` это имя: укажи `project=HubEx`, `versionType=Branch`, `version` = ветка по умолчанию (`main` / `master` / `develop`).
   - `repo_list_directory` — соседние файлы, если логика рядом.
5. Проследи цепочку: UI → запрос/ручка → сервис. Если баг на вебе, но симптом похож на API — загляни в `HubEx.Service.*.Api`.

Если `search_code` пустой или ошибка — не останавливайся: `repo_list_directory` по вероятным папкам и `repo_get_file_content` по именам из треда.

Если MCP недоступен — напиши это коротко и не выдумывай код.

## Ответ (русский)

1. **Проблема** — одно-два предложения.
2. **Где смотрел** — репозитории и ветка.
3. **Шаги воспроизведения** — по треду.
4. **Потенциальные причины** — нумерованный список. У каждой:
   - суть;
   - репозиторий, путь к файлу, функция/компонент;
   - фрагмент кода (короткий);
   - почему это может давать фактический результат.
5. **Что проверить** — 1–3 проверки, если уместно.

Не чини код и не открывай PR, если не просили. В конце можно одной строкой: чтобы завести карточку — `@Cursor создай баг`.
